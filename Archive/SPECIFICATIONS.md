# Technical Specification: Stateless QR Issuance & Localhost Staged-Verification Architecture

* **Document Reference:** `SPEC-EMS-HYBRID-2026-MSSQL`
* **Target Platform:** ASP.NET Web Forms (.NET Framework / C#)
* **Database Engine:** Microsoft SQL Server (MSSQL / T-SQL)
* **Video Ingestion:** OBS Studio (OBS Virtual Camera) via HTML5 Canvas + `jsQR`
* **System Classification:** Stateless Token Minting with Localhost Stateful Admission & Human-in-the-Loop Audit

---

## 1. System Architecture & Core Paradigm

This architecture is designed for institutional campus events operating under physical seat constraints and unreliable venue networking. It resolves the **Phantom Booking Problem** (where online registrants do not show up, leaving physical seats empty) without introducing cloud database latency or registration write locks.

```text
   ┌────────────────────────────────────────────────────────────────────────┐
   │                        ONLINE ENVIRONMENT                              │
   │                                                                        │
   │   Pre-Registrations & Hallway Walk-Ins                                 │
   │   (Mobile Browsers / Public Web Application)                           │
   │                 │                                                      │
   │                 ▼                                                      │
   │   Stateless Minting Engine (No Cloud Database)                         │
   │   • Collects 8 demographic attributes + server timestamp               │
   │   • Computes cryptographic signature (HMAC-SHA256)                     │
   │   • Streams compact pipe-delimited QR to phone screen                  │
   └─────────────────────────────────┬──────────────────────────────────────┘
                                     │ Physical Attendee Ingress
                                     ▼
   ┌────────────────────────────────────────────────────────────────────────┐
   │             PHYSICAL VENUE GATE (ASP.NET ON LOCALHOST)                 │
   │                                                                        │
   │   [Student Phone Screen] ──► [External Webcam]                         │
   │                                    │                                   │
   │                                    ▼                                   │
   │                          [OBS Virtual Camera]                          │
   │                                    │ (DirectShow / MediaStream)        │
   │                                    ▼                                   │
   │   ASP.NET Web Forms Client (`Scanner.aspx`)                            │

   │   ├─ Stage 3: Commit Guard (Capacity Check & ADO.NET Atomic Insert)    │
   │   └─ Stage 4: Visual Profile Feedback & Live Headcount Dashboard       │
   └────────────────────────────────────────────────────────────────────────┘
```

### 1.1 Architectural Separation

* **Public Web (Stateless Token Mint):** A public web page collecting student demographics that outputs a cryptographically signed QR code without writing records to a database. Pre-registrants and hallway walk-ins access this exact same registration form.
* **Local Workstation (`localhost` / `127.0.0.1`):** An ASP.NET Web Forms application backed by a local Microsoft SQL Server instance. It captures the OBS Virtual Camera stream, runs a fail-fast duplicate pre-check against MSSQL, loads attendee data into editable input fields for physical school ID verification, and commits admissions upon operator confirmation.

## 2. Cryptographic QR Data Contract

### 2.1 Pipe-Delimited Payload Structure

To avoid auto-focus lag and optical bloom when webcams scan smartphone screens, JSON keys are omitted. The payload is a compact, pipe-delimited string of 10 positional fields. `ScannedAt` is strictly excluded from the QR token and is generated by MSSQL (`SYSUTCDATETIME()`) upon physical admission.

```text
StudentID|LastName|FirstName|Branch|Department|Course|Section|Email|RegisteredAt|Signature
```

| Index | Field Name | Target T-SQL Type | Format Example | Description |
| :--- | :--- | :--- | :--- | :--- |
| **0** | `StudentID` | `VARCHAR(50)` | `2024-00123` | Institutional unique identifier. Acts as Primary Key in MSSQL. |
| **1** | `LastName` | `NVARCHAR(100)` | `Dela Cruz` | Legal surname. |
| **2** | `FirstName` | `NVARCHAR(100)` | `Juan` | Legal first name. |
| **3** | `Branch` | `NVARCHAR(100)` | `San Bartolome` | Campus branch. |
| **4** | `Department` | `NVARCHAR(100)` | `CICS` | Academic department / college. |
| **5** | `Course` | `VARCHAR(50)` | `BSIT` | Degree program. |
| **6** | `Section` | `VARCHAR(50)` | `SBIT3C` | Academic class section. |
| **7** | `Email` | `VARCHAR(150)` | `juan@univ.edu.ph` | Student contact email. |
| **8** | `RegisteredAt` | `BIGINT` | `1758878400` | Unix epoch timestamp generated at submission. |
| **9** | `Signature` | `VARCHAR(64)` | `4f8b2a...c1` | Hex-encoded HMAC-SHA256 signature. |

### 2.2 Signature Generation & Verification Formula

The HMAC is computed across indices 0 through 8:

$$\text{DataStream} = \text{StudentID} \parallel \text{"\vert{}"} \parallel \text{LastName} \parallel \text{"\vert{}"} \dots \parallel \text{RegisteredAt}$$

$$\text{Signature} = \text{HMAC-SHA256}(\text{DataStream}, \text{SharedSecretKey})$$

* **QR Code Version:** Model 2, Version 4 ($33 \times 33$) to Version 6 ($41 \times 41$).
* **Error Correction Level:** Level L (7%) or Level M (15%) to maintain maximum cell size.

## 3. Microsoft SQL Server (MSSQL) Database Schema

The persistence layer runs exclusively on the local machine within Microsoft SQL Server.

```sql

GO

    StudentID VARCHAR(50) NOT NULL,
    LastName NVARCHAR(100) NOT NULL,

    Department NVARCHAR(100) NOT NULL,
    Course VARCHAR(50) NOT NULL,

    IsWalkIn BIT NOT NULL,

ON EventAttendance (Department, Course, Section, IsWalkIn);
GO
```

## 4. Video Ingestion Pipeline (OBS Virtual Camera)

* **Hardware Configuration:** Fixed-mount external HD webcam oriented toward the attendee at table height.
* **OBS Studio Operating Parameters:**
  * Resolution locked at 1280x720 at 30 FPS (prevents USB bus throttling and frame stutter).
  * Auto-focus disabled; manual focal distance locked at 15–20 cm (6–8 inches) from the lens.
  * Auto-exposure disabled; exposure fixed to prevent backlight blowout from mobile OLED/LCD screens.
  * Virtual Camera active and assigned as system video source.
* **Web Forms Ingestion Layer (`Scanner.aspx`):**
  * Browser requests access via `navigator.mediaDevices.getUserMedia`.
  * Video frames are piped to an offscreen HTML5 `<canvas>` element at 30 FPS.
  * `jsQR` parses image byte arrays from the canvas to decode raw payload strings.

## 5. In-Person Staged-Verification State Machine

```text
                   [ Frame Decoded by jsQR in Scanner.aspx ]
                                       │
                                       ▼
             ┌───────────────────────────────────────────────────┐
             │ Gate 1: Cryptographic Signature Verification      │
             │ Recompute HMAC-SHA256 with local shared secret.   │
             └─────────────────────────┬─────────────────────────┘
                                       │ Valid
                                       ▼
             ┌───────────────────────────────────────────────────┐
             │ Gate 2: Fail-Fast MSSQL Duplicate Pre-Check       │
             │ AJAX -> [WebMethod] ValidateAndPreCheck(payload)  │
             │ SELECT ScannedAt FROM EventAttendance WHERE ...   │
             └─────────────────────────┬─────────────────────────┘
                                       │
          ┌────────────────────────────┴────────────────────────────┐
          │ Record Found (Duplicate)                                │ Record Not Found (Clean)
          ▼                                                         ▼

                                                     └────────────────────────────────────────┘
```

### 5.1 Verification Gate Mechanics

#### Gate 1: Cryptographic Validation
* Upon frame acquisition, the payload is split by `|`.
* If parts count $\neq 10$, reject as malformed.
* Recompute `HMAC-SHA256` across indices 0 through 8 using the shared secret. If mismatch, halt with **Red: Invalid Signature**.

#### Gate 2: Fail-Fast MSSQL Duplicate Pre-Check
* `Scanner.aspx` makes an asynchronous AJAX call to a C# `[WebMethod]`.
* Query executed:
  ```sql
  SELECT ScannedAt FROM EventAttendance WHERE StudentID = @StudentID;
  ```
* **Collision Behavior:** If `ScannedAt` is returned, trigger an immediate **Red (Duplicate / Anti-Passback Alert)** displaying the original scan timestamp. The review form fields remain cleared and locked, preventing wasted manual audit time on reused tickets.
* **Clean Behavior:** The server converts `RegisteredAt` Unix timestamp to readable UTC and determines walk-in status:
  $$\text{IsWalkIn} = \begin{cases} 1 & \text{if } \text{RegisteredAt} \ge \text{EventStartTime} \\ 0 & \text{if } \text{RegisteredAt} < \text{EventStartTime} \end{cases}$$
  Populates form inputs on the UI and sets status to **`PENDING AUDIT`**.

#### Gate 3: Operator Audit & Human-in-the-Loop Cross-Match
* The operator requests the student's physical institutional ID card.
* The operator verifies the photo, name, and student number match the screen.
* The operator corrects any typos (e.g., misspelled name or wrong section) directly in the UI text boxes.

#### Gate 4: Commit Guard & Atomic Insert
* Triggered when the operator presses <kbd>Enter</kbd> or clicks **Confirm & Admit**.
* **Capacity Guard:** Executes `SELECT COUNT(1) FROM EventAttendance`. If `CurrentCount >= MaxCapacity`, admission terminates with **Red: Venue Capacity Reached**.
* **Database Commit:** Executes a parameterized ADO.NET `INSERT`. If the operator manually modified `StudentID` to an ID already admitted earlier, the `PRIMARY KEY` constraint blocks the transaction and warns the operator.
* Updates live dashboard counter and clears fields for the next frame.

## 6. Physical Gate Operations & Walk-In Ingestion

```text
                       HALLWAY TRAFFIC
                             │
                             ├─► [Does Attendee Have QR Code?]
                             │
              ┌──────────────┴──────────────┐
              │ NO                          │ YES
              ▼                             ▼
   [Lane B: Holding Area]          [Lane A: Active Scan Lane]
   • Scan Entrance Poster QR       • Present phone screen to webcam
   • Submit details on phone       • 15–20cm distance from lens
   • Mint signed entry pass        • Hold physical student ID card
              │                             │
              └──────────────┬──────────────┘
                             ▼
                [OBS Video Capture Station]
                             │
                             ▼
                [Operator Audit & Admission]
```

* **Lane A (Fast Ingress):** Dedicated strictly to attendees displaying an active QR pass on their phone screen.
* **Lane B (Poster Wall Holding Area):** Positioned 5 to 10 meters away from the doorway. Attendees without tickets scan a physical printed poster displaying the registration URL, fill out the form, generate their signed pass, and then join Lane A. This keeps unfinished registrations out of the active door line.
* **Capacity Hard Cutoff:** If pre-registered no-shows leave open seats, walk-in attendees claim them sequentially. Once `COUNT(*) == MaxCapacity`, the system transitions to a hard lockout, rejecting further admissions to enforce safety codes.

### Dashboard UI State Rules

* **Idle / Scanning:** Background neutral; inputs disabled and cleared; status indicator displays gray `AWAITING CAMERA SCAN...`.
* **Duplicate Detected:** Screen border flashes red; error tone sounds; status displays `ANTI-PASSBACK ALERT: TICKET ALREADY REDEEMED AT [TIMESTAMP]`. Inputs remain disabled and cleared.
* **Pending Audit:** Chime sounds; inputs populate and become editable (`StudentID` remains locked); badge displays `[PRE-REGISTERED]` (Blue) or `[WALK-IN]` (Amber); confirm button gains focus; status turns yellow `READY FOR AUDIT: Verify ID & Press ENTER`.
* **Admitted:** Screen flashes green; status displays `ADMITTED: [NAME] [COUNT / MAX]`; counter increments; form resets after 1000ms.
* **Venue Full:** Status displays red `VENUE CAPACITY REACHED - ENTRY HALTED`; admission commits disabled.

## 8. Post-Event Analytical Suite (T-SQL)

Because all student demographics and check-in timestamps are consolidated in the local database, you can run immediate post-event queries in SSMS without data cleaning or cloud synchronization:

### 8.1 Seating Capacity Yield & Walk-In Absorption Rate

```sql
SELECT 
    COUNT(1) AS TotalPhysicalAttendees,
    SUM(CASE WHEN IsWalkIn = 0 THEN 1 ELSE 0 END) AS PreRegisteredAttendees,
    SUM(CASE WHEN IsWalkIn = 1 THEN 1 ELSE 0 END) AS WalkInsAbsorbed,
    CAST(COUNT(1) * 100.0 / 100 AS DECIMAL(5,2)) AS VenueFillRate, -- Assumes 100 Seat Cap
    -- Walk-In Absorption Efficiency: (Walk-Ins / Empty Seats Reclaimed)
    CAST(
        SUM(CASE WHEN IsWalkIn = 1 THEN 1 ELSE 0 END) * 100.0 / 
        NULLIF(100 - SUM(CASE WHEN IsWalkIn = 0 THEN 1 ELSE 0 END), 0)
        AS DECIMAL(5,2)
    ) AS WalkInAbsorptionEfficiencyRate
FROM EventAttendance;
```

### 8.2 Attendance Demographics Breakdown

```sql
SELECT 
    Department, 
    Course, 
    Section,
    COUNT(1) AS TotalPresent,
    SUM(CASE WHEN IsWalkIn = 0 THEN 1 ELSE 0 END) AS PreRegCount,
    SUM(CASE WHEN IsWalkIn = 1 THEN 1 ELSE 0 END) AS WalkInCount
FROM EventAttendance
GROUP BY Department, Course, Section
ORDER BY TotalPresent DESC;
```

### 8.3 Multi-Factor Punctuality Bracket Audit

```sql
SELECT 
    CASE 
        WHEN ScannedAt < '2026-09-26 13:00:00' THEN 'Early Arrival (<T+0)'
        WHEN ScannedAt BETWEEN '2026-09-26 13:00:00' AND '2026-09-26 13:15:00' THEN 'On-Time (T+0 to T+15)'
        ELSE 'Late Arrival (>T+15)'
    END AS PunctualityBracket,
    COUNT(1) AS TotalCount,
    SUM(CASE WHEN IsWalkIn = 1 THEN 1 ELSE 0 END) AS WalkInsInBracket
FROM EventAttendance
GROUP BY 
    CASE 
        WHEN ScannedAt < '2026-09-26 13:00:00' THEN 'Early Arrival (<T+0)'
        WHEN ScannedAt BETWEEN '2026-09-26 13:00:00' AND '2026-09-26 13:15:00' THEN 'On-Time (T+0 to T+15)'
        ELSE 'Late Arrival (>T+15)'
    END;
```

## 9. Directives for the AI Coding Agent

When implementing this codebase, adhere strictly to these technical requirements:

1. **Maintain Statelessness in Online Registration:** Do not attach a database connection string or ORM context to the online registration form. The registration server must strictly format the pipe-delimited payload, calculate the HMAC-SHA256 signature, and stream the QR code to the browser.
2. **Prevent Database Injection:** Use parameterized SQL commands exclusively (`cmd.Parameters.Add("@Param", SqlDbType.VarChar)`). Never concatenate strings into SQL queries.
3. **Preserve Primary Key Constraints:** The clustered primary key on `StudentID` in MSSQL is the single source of truth for anti-passback protection. Never bypass or remove this constraint.
4. **Prevent Premature Form Population:** The fail-fast duplicate pre-check in `Scanner.aspx` must return before populating the form fields. If a duplicate is detected, the form inputs must remain disabled and clear.
5. **Debounce Video Scanning:** A boolean lock (`isScanningLocked`) must remain true while a code is being processed or audited to prevent the camera loop from firing repeated AJAX calls on the same video frame.
6. **Keyboard Handling:** Wire the global <kbd>Enter</kbd> keydown event to submit the staged verification form only when the system is in the `PENDING AUDIT` state. Ensure pressing <kbd>Enter</kbd> while inside an `<input>` field executes the commit guard rather than triggering accidental page reloads.
